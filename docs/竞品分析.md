# 竞品分析：知识库问答方案

## 1. 分析目的

明确本项目的定位与差异化，判断"领域知识库问答"方案的选择逻辑。

## 2. 竞品对比

| 维度 | 通用大模型（如 ChatGPT） | 企业知识库产品（如 Dify） | 本项目 |
|---|---|---|---|
| 领域知识 | 无，需用户自行提供 | 支持上传文档 | 内置公交客流领域知识 |
| 来源可追溯 | 不支持 | 部分支持 | 每条结论标注来源 |
| 幻觉控制 | 弱 | 中等 | 强（无依据即拒答） |
| 部署成本 | 低 | 中（需部署平台） | 低（零依赖） |
| 可定制性 | 低 | 高 | 高（代码级可控） |
| 评测体系 | 无 | 基础 | 完整（检索/生成分层） |

## 3. 差异化定位

本项目不是要做通用知识库平台，而是验证一个**面向垂直领域、以可信为核心的知识问答原型**：

- **可信优先**：带引用 + 明确拒答，直击数据分析场景的幻觉痛点
- **可解释**：检索与生成分离评估，问题可定位到具体模块
- **轻量可迁移**：零依赖运行，便于演示；架构清晰，可平滑升级为向量检索方案

## 4. 为何不直接选 Dify / Coze

低代码平台搭建快，但两个问题：
1. 黑盒化强，难以展示对 RAG 各环节（切分、召回、Prompt、拒答）的理解；
2. 求职场景中，"能讲清每个环节为什么这么设计"比"能用工具搭出来"更有说服力。

因此本项目选择手写核心链路，把技术决策暴露出来，作为产品经理技术理解力的证据。

## 5. 结论

在"快速搭建"与"深度理解"之间，本项目选择后者。这一定位契合 AI 产品经理岗位对"技术边界判断力"和"效果评估能力"的要求，而非与低代码平台比拼搭建速度。
